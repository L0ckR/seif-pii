# Выбор стека: Python 3.14 без GIL, процессы или Go

Дата проверки документации и пакетов: **22 сентября 2026 года**.

**Рекомендация для СЕЙФА — Python 3.14.7 free-threaded с ограниченным пулом для длинных текстов, FastAPI/Uvicorn и Redis.** Локальная проверка обнаружила реальное масштабирование детектора в четырёх потоках и подтвердила работу необходимых импортов без GIL. Короткие запросы целесообразно оставить на прямом пути до отдельного измерения цены передачи в пул. Дополнительное масштабирование — несколько процессов Uvicorn с общим Redis. Переписывание на Go пока не подтверждено профилем затрат и потребует повторной проверки распознавания.

Это решение опирается на измеренный **CPU-микробенчмарк**, а не на предположение об ускорении HTTP в три раза. Результаты нагрузки API нужно читать отдельно, вместе с конфигурацией запуска и исходными JSON-отчётами. Точная сборка для внедрения — `3.14.7t`; обычная `3.14.7` остаётся контрольной конфигурацией.

## Что уже измерено

На Linux x86-64 / WSL2 с 16 видимыми логическими CPU выполнено по 20 000 вызовов детектора на четырёх синтетических текстах. Числа отражают отдельный диагностический запуск, не длительный нагрузочный тест:

| Runtime | 1 поток, вызовов/с | 4 потока, вызовов/с | Отношение 4 / 1 |
|---|---:|---:|---:|
| Обычный CPython 3.14.7 | 10 773 | 11 084 | 1,03× |
| CPython 3.14.7t, GIL выключен | 10 455 | 33 290 | 3,18× |
| Та же сборка 3.14.7t, GIL включён | 11 652 | 11 121 | 0,95× |

Исходные результаты: [обычный 3.14](runtime-314.json), [3.14t без GIL](runtime-314t.json), [3.14t с GIL](runtime-314t-gil.json). В отчётах зафиксированы версии, платформа, состояние GIL после импортов и границы измерения. HTTP, Redis и сеть в эти числа **не входят**. Однопоточная скорость 3.14t без GIL в этой серии примерно на 3% ниже обычной сборки; одного прогона недостаточно для вывода о стабильной величине различия.

В 3.14t GIL оставался выключенным после импортов FastAPI, `pydantic_core`, AES-GCM из `cryptography`, `regex`, PyYAML, Redis, uvloop и httptools. На обычном 3.14.7 и 3.14.7t прошли по **139 тестов** существующего набора. Это подтверждает проверенные сценарии, но не заменяет длительный конкурентный тест и проверку качества на независимом корпусе.

Инженерный вывод: 3.14t оправдан как основной кандидат для внедрения — он сохраняет текущие правила и даёт измеренный прирост при реальном параллельном вызове детектора. Решение о количестве API-workers и итоговый предел RPS должны опираться на отдельную HTTP-серию с одинаковым Redis и лимитами.

## Что действительно меняет Python 3.14

Free-threaded сборка в Python 3.14 официально поддерживается и больше не считается экспериментальной. Она остаётся **отдельной, необязательной сборкой**: обычный Python 3.14 по умолчанию сохраняет GIL. Нельзя считать обновление номера версии автоматическим включением многопоточного исполнения. [Python 3.14: статус free-threading](https://docs.python.org/3.14/whatsnew/3.14.html#free-threaded-python-is-officially-supported).

Сборка без GIL позволяет Python-потокам выполняться на разных ядрах. Поддержку сборки проверяют через `sysconfig.get_config_var("Py_GIL_DISABLED")`, фактическое состояние процесса — через `sys._is_gil_enabled()`. Эти проверки отвечают на разные вопросы: импорт неподготовленного нативного расширения способен включить GIL обратно. Наличие дополнительных расходов на исполнение и память означает, что ускорение однопоточного сценария не гарантировано. [Руководство Python по free-threading](https://docs.python.org/3.14/howto/free-threading-python.html).

**Снятие GIL не распределяет корутины одного event loop между ядрами.** Синхронный расчёт внутри обработчика удерживает поток цикла событий до завершения. Для параллельной обработки CPU-задач нужен явный переход в другой поток, интерпретатор или процесс. [Python: блокирующий код в asyncio](https://docs.python.org/3.14/library/asyncio-dev.html#running-blocking-code).

`asyncio.to_thread()` создаёт такую границу исполнения; при обычном GIL его польза для CPU-нагрузки зависит от того, освобождает ли используемый нативный код GIL. [Python: asyncio.to_thread](https://docs.python.org/3.14/library/asyncio-task.html#asyncio.to_thread). Например, библиотека `regex` документирует освобождение GIL при сопоставлении с неизменяемыми строками. Но основной детектор СЕЙФА использует стандартный `re`, а `regex` — для дополнительных правил с тайм-аутом. Замена одного движка другим требует проверки результатов и собственного замера. [Документация автора regex](https://github.com/mrabarnett/mrab-regex/blob/hg/README.rst#multithreading).

## Как это относится к текущему коду

Исходная архитектура, от которой выполнялась оценка:

| Участок | Реализация | Следствие для выбора стека |
|---|---|---|
| HTTP | FastAPI, Uvicorn; исходный Docker на `python:3.13-slim` | Переход на выбранную 3.14.7t требует явно закрепить free-threaded runtime |
| Детекция | `seif/detector.py`: `re`, Python-контекст, проверки контрольных сумм, разрешение перекрытий | Нужно профилировать весь `detect()`, а не отдельно один regex |
| Короткий текст | `detect()` синхронно в `async`-обработчике | Простая замена интерпретатора на 3.14t не создаёт параллельный CPU-путь |
| Текст длиннее 16 000 символов | `await asyncio.to_thread(detect, ...)` | Здесь уже есть место для проверки масштабирования потоков |
| Преобразование и хранилище | Подстановки, JSON, HMAC, AES-GCM; Redis через `redis.asyncio` | Ускорение детекции не равно ускорению полного HTTP-запроса |
| Локальное хранилище | Память процесса и `asyncio.Lock` | Нельзя использовать как общее хранилище нескольких процессов или произвольно разделять между event loop |
| Метрики | Отдельный `CollectorRegistry` в каждом приложении | Для нескольких процессов понадобится корректный сбор и суммирование метрик |

Вывод из кода и микробенчмарка: внедрить ограниченный пул из четырёх потоков для детекции длинных текстов, сохранив сетевые операции и хранилище на одном event loop. Порог переноса коротких запросов нужно выбирать измерениями: стоимость постановки задачи может оказаться выше экономии. Измеренные 33 290 вызовов/с получены на коротком тексте в отдельном пуле; они доказывают возможность параллельного исполнения, но не измеряют производительность длинных документов.

Если вместо этого запускать несколько event loop в потоках и разделять один экземпляр приложения, придётся отдельно защищать счётчики, ограничения частоты, хранилище и составные операции над состоянием. Внутренняя защита отдельных операций контейнеров не делает произвольный алгоритм потокобезопасным. [Python: thread safety](https://docs.python.org/3.14/howto/free-threading-python.html#thread-safety).

Таким образом, нельзя заранее отвергать 3.14t с аргументом «для uvloop или cryptography нет сборок». Но колесо означает наличие устанавливаемого артефакта, а не доказанную корректность нашего приложения при конкурентном исполнении. Нативные расширения должны отдельно декларировать поддержку работы без GIL; free-threaded ABI отличается от обычного. [Python: подготовка расширений](https://docs.python.org/3.14/howto/free-threading-extensions.html).

При повторении проверки нужно устанавливать **тот же lock-файл** в отдельное окружение 3.14t, импортировать реальные нативные подмодули, вызывать AES-GCM и валидацию Pydantic, затем повторно проверять состояние GIL. Проверять только `import cryptography` недостаточно: часть расширений загружается лениво. Затем выполняются тесты API, точного восстановления, Unicode, TTL, конкурентных повторов и отказов. Репозиторий содержит соответствующие тесты в `tests/test_api.py` и `tests/test_detector.py`; проверенный выше прогон на 3.14t включает этот набор.

Первичную проверку следует проводить без принудительного `-X gil=0`, чтобы увидеть автоматическое включение GIL несовместимым расширением. Принудительное выключение не исправляет расширение. Для диагностики HTTP можно отдельно сравнить `--loop asyncio --http h11` и `uvloop/httptools`; это разные конфигурации, их нельзя молча смешивать в таблице результатов. [Настройки Uvicorn](https://uvicorn.dev/settings/#implementation).

## Процессы и Redis

Uvicorn поддерживает несколько worker-процессов через `--workers`. Каждый процесс исполняет свой Python независимо, поэтому CPU-параллелизм доступен и с обычным GIL. [Uvicorn: process manager](https://uvicorn.dev/deployment/#built-in).

В СЕЙФЕ это требует общего Redis, одинакового `SEIF_MASTER_KEY` и согласованных политик во всех workers. Маскирование может попасть в один процесс, восстановление — в другой; память отдельного worker для этого недостаточна. Текущий Redis-путь уже использует `SET NX` для фиксации одного соответствия и Redis-счётчик частоты. Это делает архитектуру пригодной для проверки нескольких workers, но не доказывает результат нагрузки заранее.

Цена подхода — отдельные интерпретаторы и кэши, обращения к Redis и необходимость наблюдать все workers. Сравнивать нужно суммарный RSS, CPU и задержку под нагрузкой. Общий Redis нельзя исключить только из одной стороны сравнения: тогда измеряется одновременно runtime и другая схема хранения.

## Что даст переход на Go и сколько он стоит

Go позволяет параллельное исполнение на нескольких CPU; количество одновременно исполняющих CPU контролируется `GOMAXPROCS`. Это делает его естественным кандидатом для сервиса с большим числом конкурентных CPU-задач. Сам по себе язык не гарантирует выигрыш на конкретном наборе правил. [Go runtime: GOMAXPROCS](https://pkg.go.dev/runtime#GOMAXPROCS).

Преимущество стандартного `regexp` в Go — гарантия времени поиска, линейного по размеру входа. Скомпилированный `Regexp` допускает конкурентное использование, кроме методов его настройки. Это полезные свойства для обработки недоверенного текста. [Go regexp](https://pkg.go.dev/regexp).

Однако перенос текущего детектора не сводится к переписыванию HTTP-обработчика:

| Различие | Значение для СЕЙФА |
|---|---|
| Lookaround | Текущие правила используют `(?<!...)`, `(?!...)`, `(?=...)`. RE2 не поддерживает эти конструкции; проверки границ и контекста нужно вынести в код или переработать правила. [RE2 syntax](https://github.com/google/re2/wiki/Syntax) |
| Unicode-границы | В Go `\w`, `\d`, `\s` и `\b` имеют ASCII-семантику; Unicode-классы задаются отдельно. Прямой перенос `\bпаспорт` может изменить результат. [Go regexp/syntax](https://pkg.go.dev/regexp/syntax) |
| Python-семантика | В текущих строковых шаблонах Python `\w` и граница `\b` учитывают Unicode. На этом основаны русские метки и проверки соседних символов. [Python re](https://docs.python.org/3.14/library/re.html#regular-expression-syntax) |
| Смещения | Go-методы `Index` возвращают позиции в байтах UTF-8. API СЕЙФА возвращает позиции Unicode code points; потребуется явное преобразование. [Go regexp: формат индексов](https://pkg.go.dev/regexp#pkg-overview) |
| Правила пользователей | Нужно заново определить поддерживаемый синтаксис, ограничения и поведение тайм-аутов; текущий контракт основан на `regex` |
| Поведение продукта | Публичные имена, адреса банков, склонения, перекрытия и точное восстановление должны пройти одинаковые тесты до сравнения скорости |

Следствие: Go становится разумным выбором, если профиль показывает устойчивое CPU-ограничение детектора, Python-варианты не укладываются в нужную стоимость/latency, а эквивалентность извлечения подтверждена общим корпусом. Возможен и небольшой отдельный детектор на Go с неизменным внешним API. Это направление исследования, не готовый компонент текущего решения.

## Как сравнивать варианты честно

Минимальная матрица — обычный CPython 3.14, 3.14t с GIL, 3.14t без GIL; отдельно сохранённый baseline 3.13. Сравнение только 3.13 и 3.14t смешивает эффекты новой версии, сборки и GIL. Для каждой записи нужны точная версия Python, состояние GIL после импортов, CPU/cgroup-ограничения, число процессов/потоков, HTTP-парсер, event loop, storage и зафиксированные зависимости.

Нужны два разных измерения:

1. **Детектор:** одинаковый корпус, один и несколько потоков; символы/с, задержка, загрузка ядер и идентичность найденных spans. Это проверяет возможность масштабирования CPU.
2. **Сервис:** весь маршрут HTTP → валидация → детекция → шифрование → хранилище → восстановление. Отдельные серии коротких и длинных текстов, уникальные идентификаторы, корректность каждой пары, successful RPS, p95/p99, ошибки, RSS и нагрузка Redis. Это проверяет пользовательский результат.

В `scripts/benchmark.py` уже есть генератор с заданной частотой начала пар и проверкой восстановления. Его штатный корпус состоит из коротких строк и не активирует порог `to_thread` для длинного текста. Он измеряет полный `/process`, а не только `detect()`. Запуск клиента на тех же CPU способен ограничить результат, поэтому нужно учитывать отставание генератора и исчерпание клиентской конкурентности.

Для итогового выбора предпочтительны повторные серии после прогрева, одинаковый бюджет CPU/RAM и отдельный генератор нагрузки. Замер через публичный туннель полезен для проверки доступности, но включает внешнюю сеть и не изолирует цену интерпретатора.

**Прогноз, требующий проверки:** измеренный выигрыш 3.14t в параллельных вызовах детектора может улучшить пропускную способность на длинных независимых текстах; несколько обычных workers могут оказаться выгоднее на коротких HTTP-запросах; Go может снизить стоимость CPU после полноценного переноса правил. Эти три предположения не следуют автоматически из приведённого микробенчмарка. Выбор runtime также не повышает автоматически качество распознавания на скрытой выборке.
