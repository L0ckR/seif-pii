# Матрица требований и приёмки

Источник требований — предоставленный пользователем `ds.pdf`; исходный документ в архив решения не включён. Этот документ отделяет реализованные механизмы от доказательств, которые могут дать только внешняя проверка и эксплуатация в банковском контуре.

## 1–3. Назначение, образ решения, ключевые требования

| Пункт ТЗ | Реализация | Проверка и границы |
|---|---|---|
| 1. Определить тип, замаскировать, демаскировать | Локальный детектор, три способа замены, зашифрованное хранилище соответствий | `scripts/evaluate.py`, `tests/test_api.py` |
| 2. Обработать запрос до LLM и ответ после LLM | `/v1/mask` перед вызовом модели, `/v1/unmask` после; token-режим восстанавливает известные токены в изменённом ответе | Проверяется восстановление повторённых токенов в новом тексте. Сам сервис не вызывает внешнюю LLM |
| 2. Качество, ложные срабатывания, сохранение смысла | Контекстные правила, проверки форматов/контрольных сумм, исключения публичных упоминаний; типизированные токены | Не является универсальным NER: разговорные, неоднозначные и новые форматы требуют расширения правил |
| 2. Настройки систем, подключение нового потребителя | Политики `config/policies.yaml`, заголовки `X-System-ID`, `X-API-Key` | Проверяются доступ, изоляция систем, отключение демаскирования и типы |
| 2. Ошибки компонентов и отсутствие ПД в телеметрии | Защита fail-closed, контролируемые ошибки, аудит без текста и `payload_id` | Тесты сбоя детектора, нарушения целостности ciphertext, проверки логов и метрик |
| 2–3. Расширение, интеграция, скорость, безопасность | Отдельные модули детектора, преобразования, хранилища и HTTP; Redis для общих соответствий | Redis и горизонтальные экземпляры требуют общей конфигурации и ключа; соответствие внутренним стандартам банка проверяется отдельно |

## 4.1. Типы персональных данных

| Требование | Идентификаторы детектора | Принцип |
|---|---|---|
| ФИО | `PERSON` | ФИО, инициалы, известные имена и контекст личной записи; без зависимости от регистра |
| Дата рождения | `BIRTH_DATE` | Контекст рождения, числовые и текстовые даты, проверка календарной корректности |
| Место рождения | `BIRTH_PLACE` | Метка места рождения |
| Паспорт РФ, серия и номер | `PASSPORT` | Форматы слитно, с разделителями, словами «серия» и «номер» |
| Гражданство | `CITIZENSHIP` | Гражданство и распространённые названия стран |
| Орган выдачи паспорта | `PASSPORT_ISSUER` | Контекст выдачи, МВД/УФМС/ОВД и подразделения |
| Код подразделения | `DEPARTMENT_CODE` | Контекстная шестизначная запись с разделителем |
| Дата выдачи паспорта | `PASSPORT_DATE` | Контекст выдачи и календарная дата |
| Водительское удостоверение | `DRIVER_LICENSE` | Числовые и буквенные серии, полное и сокращённое наименование |
| Адрес и отдельные компоненты | `ADDRESS`, `COUNTRY`, `POSTAL_CODE`, `CITY`, `STREET`, `HOUSE`, `APARTMENT` | Полный адрес возвращается одним спаном; отдельные компоненты распознаются по собственным меткам |
| Email | `EMAIL` | Формат адреса, регистронезависимо |
| Телефон | `PHONE` | Российские и международные формы, разделители и контекст |
| ИНН | `INN` | Явная метка либо контрольная сумма для голого номера |
| Номер банковской карты | `CARD` | Явная метка либо Luhn для номера без метки |
| CVV | `CVV` | Только в соответствующем контексте |
| ПИН-код карты | `PIN` | Только в соответствующем контексте |
| Имя держателя карты | `CARDHOLDER` | Латиница/кириллица и явная метка держателя |

Публичное упоминание поэта и адрес отделения банка проверяются отрицательными примерами; явный контекст клиента имеет приоритет. Это эвристика, а не юридическое определение персональных данных: неоднозначные случаи требуют согласованной банковской политики. Новые типы добавляются через `extra_rules`; пользовательские регулярные выражения ограничены по длине и времени исполнения. В аудит каждого успешного запроса пишутся выявленные типы без их значений.

## 4.2–4.4. Преобразования и общие требования

| Пункт ТЗ | Реализация | Доказательство / ограничение |
|---|---|---|
| 4.2. Регистр | Правила `IGNORECASE` | Нижний и верхний регистр в независимых примерах |
| 4.2. Перестановка компонентов даты | Проверяются допустимые варианты числового дня/месяца и положение года | Не производится рискованная нормализация исходной даты |
| 4.2. Даты словами, слова-разделители | Текстовые месяцы, контекстные поля и серии документов | Исходная орфография сохраняется для точного восстановления |
| 4.3. Демаскирование с сохранением знаков | В `mask` меняются буквенно-цифровые символы внутри спанов; разделители и Unicode сохраняются; восстановление по исходным сегментам | Тест на пунктуацию, emoji, перевод строки, табуляцию и комбинируемый знак; полный roundtrip |
| 4.4. Подробное логирование этапов | Структурированное событие запроса с `stages_ms` для `authorize`, `fingerprint`, `vault_read`, `detect`, `transform`, `vault_write`, `restore` по пройденным этапам и соответствующие гистограммы | Один JSON на запрос; без payload, original, маски, ключа API и идентификатора корреляции; детали внутренних исключений не выдаются |
| 4.4. Latency, RPS, TPS | Prometheus `/metrics`: длительность HTTP и стадий, счётчик запросов, символов и оценённых токенов | RPS/TPS — `rate()` соответствующих счётчиков. TPS оценивается как символы / 4; это не точный счётчик tokenizer конкретной LLM |
| 4.4. Ограниченный список систем | Явно заданные политики, включение/отключение, проверка ключей | Анонимный `demo` допускается только в явно включённом демонстрационном режиме |
| 4.4. Типы и демаскирование по системе | `types`, `allow_unmask`, `mode`, `allowed_modes` | Изоляция пространств корреляции, запрет демаскирования проверены тестами |
| 4.4. Инструкция не более 5 предложений | Пять предложений ниже | Настройки применяются перезапуском процесса |
| 4.4. Качество 95% | Есть воспроизводимая exact-span оценка, измеряющая precision/recall/F1 | `docs/evaluation.json` — результаты маленького синтетического набора разработки; **95% на закрытом наборе не заявляется** |
| 4.4. До 100 000 токенов | Лимит 2 000 000 Unicode-символов и 12 100 000 байт тела; тексты длиннее 16 000 символов идут в ограниченный CPU-пул | Есть отдельная проверка ровно 100 000 токенов `cl100k_base` (`scripts/large_input.py`). Перегрузка пула даёт `429`; отмена HTTP не освобождает слот до завершения работы. Длительность больших запросов измеряется отдельно |

### Настройка за пять предложений

1. В `config/policies.yaml` добавьте систему, задайте `enabled` и имя переменной окружения с ключом в `api_key_env`.
2. В окружении задайте этот ключ и `SEIF_MASTER_KEY`, содержащий base64 от 32 случайных байт; для общей памяти экземпляров укажите `SEIF_REDIS_URL`.
3. Установите `types`, `mode`, `allowed_modes`, `allow_unmask`, `min_types` и `required_types` под правила этой системы.
4. При необходимости добавьте `extra_rules` с полями `type` и `pattern`, задайте `rps` и перезапустите сервис.
5. Передавайте `X-System-ID` и `X-API-Key`, создавайте новый `payload_id` для каждого текста и повторно используйте его для восстановления и ретраев.

## 5. Нефункциональные требования

| Требование | Механизм | Граница доказанности |
|---|---|---|
| Защищённый контур, стандарты банка | Локальная обработка, AES-256-GCM, TTL, отсутствие внешней LLM, конфигурация без секретов | Публичный туннель — стенд с синтетикой. Он не является банковским защищённым контуром и не подтверждает соответствие внутренним стандартам |
| Надёжность и деградация | `400/422` для неверного запроса, `401/403` для доступа, `409` для конфликта, `410` для отсутствующего соответствия, `413` для размера, `429` + `Retry-After`, `503` при отказе защиты | При ошибке защиты исходный текст не возвращается вместо результата; недоступность Redis не вызывает переход к несогласованной памяти |
| Latency ≤ 1 с, RPS 1000 | Асинхронный HTTP, предварительно собранные правила, ограничение нагрузки и общая память Redis | Проверяется HTTP-генератором `scripts/benchmark.py`; короткий локальный прогон не эквивалентен пяти минутам внешнего теста |
| Масштабируемость | Stateless HTTP-экземпляры с общим Redis, мастер-ключом и одинаковыми политиками; атомарное `SET NX` для корреляции | Память `memory` применяется только одним процессом; число записей и Redis maxmemory рассчитываются по частоте новых пар и TTL |

## 7 и приложения A–B. Внешняя приёмка

1. **7.1 — ZIP исходного кода.** Перед передачей проверяется состав архива: исходники и конфигурация, без `.venv`, зависимостей, секретов, бинарников, датасетов и служебных каталогов. Наличие ZIP не означает прохождение внешней проверки качества кода: итог появляется только после его загрузки в систему организатора.
2. **7.2 — доступный URL.** Для внешнего прогона должен работать HTTPS/HTTP URL сервиса; туннель зависит от запущенного локального сервера и процесса туннеля. Приложение само не отправляет данные в систему организатора.
3. **Приложение A — контракт.** `POST /process` принимает только строковые `payload` и `payload_id`, успешный ответ содержит ровно `{"result":"…"}`. Первый новый ID маскирует, ранее выданная маска с тем же ID восстанавливается; повтор исходного или замаскированного запроса возвращает тот же результат.
4. **Приложение B — ретраи и нагрузка.** Сервер поддерживает безопасные повторы и `Retry-After`; сохранённый ID с другим содержимым даёт `409`. Генератор отправляет синтетические пары, измеряет фактическую скорость, все статусы, roundtrip-ошибки, p50/p95/p99 и отброшенную клиентом нагрузку, не подменяя её заданным RPS.
5. **Приложение B — метрика качества.** Локальная точная span-F1 отличается от нормированного span-based расстояния Левенштейна закрытого эталона. Внешний прогон с таймаутом 10 с, ретраями и правилом остановки после 5 невалидных ответов является отдельным обязательным этапом.

## Повторение проверок

```bash
.venv/bin/python -m pytest -q
SEIF_TEST_REDIS_URL=redis://127.0.0.1:6385/15 .venv/bin/python -m pytest tests/test_redis.py -q
.venv/bin/python scripts/evaluate.py --output output/quality.json
.venv/bin/python scripts/benchmark.py --url http://127.0.0.1:8000 --rps 1000 --duration 300 --concurrency 256 --output output/benchmark-1000.json
```

Пять минут при 1000 HTTP RPS дают приблизительно 150 000 новых пар; при 2000 RPS — 300 000. Если TTL больше окна проверки, хранилище должно вместить все эти пары; пределы памяти и число записей важны так же, как скорость обработки. Итоговые числа нужно брать из реально сформированных JSON-отчётов, включая ошибки и клиентские пропуски.

Redis-тесты включаются только явно заданной переменной окружения; они проверяют независимые HTTP-экземпляры, переживание перезапуска приложения, 64 конкурентные попытки атомарной записи и TTL. Удаляются только собственные UUID-записи теста, база целиком не очищается. `seif_entities_total` считает успешные запросы с данным типом, включая повторы и демаскирование, а не количество отдельных исходных сущностей.

Для нескольких workers используется `scripts/serve.py`: он создаёт общий временный `PROMETHEUS_MULTIPROC_DIR` до импорта метрик, и `/metrics` агрегирует workers данного supervisor. У каждого контейнера должен быть собственный каталог метрик; контейнеры опрашиваются отдельно, их показатели суммируются в Prometheus. Общие Redis, `SEIF_MASTER_KEY` и политики обязательны независимо от того, включён ли GIL; `/health` показывает фактический runtime, а `SEIF_REQUIRE_FREE_THREADING=1` останавливает запуск без требуемого режима.

`scripts/failover_check.py prepare --baseurl URL --state /tmp/seif-check.json` сохраняет синтетическое соответствие в приватном клиентском файле. После управляемого оператором изменения primary или API-реплики команда `verify` с теми же аргументами проверяет точное восстановление; ключи HTTP читаются только из `SEIF_TEST_SYSTEM`/`SEIF_TEST_API_KEY`. Такая проверка фиксирует сохранение конкретной пары, но не доказывает отсутствие потерь при асинхронной репликации Redis и не заменяет измерение RTO/RPO.
