# Проверки решения

Измерения выполнены 22 сентября 2026 года на локальном Linux/WSL2 x86-64, AMD Ryzen 7 7800X3D (8 ядер / 16 логических CPU). Генератор и сервис находятся на одном компьютере; все входные данные синтетические. Это проверка реализации, а не результат закрытой оценки организатора.

## Функциональные проверки

- Полный набор после улучшений по итогам изучения Presidio: **219 passed** на CPython 3.14.7 и 3.14.7t, включая настоящий Redis и отключение primary в изолированной группе из трёх Redis и трёх Sentinel. Сюда включены 32 новые регрессионные проверки контекста; полный набор также запускается в CI.
- 48 примеров разработки: precision = recall = exact-span F1 = 1.0 ([сырые результаты](evaluation.json)); набор использовался для исправления правил и не считается независимым holdout.
- Эталонный `/process` из Приложения B проверен отдельным запросом: ответ `{"result":"тестовая строка"}` соответствует контракту. Это проверка формата, а не оценка качества нашего сервиса.
- Проверены настоящий браузер Chromium, режимы защиты и восстановление; мобильный интерфейс проверен на ширине 390 px.
- GitHub Actions проверяет обе сборки Python, собирает контейнер, запускает его с отключённым GIL, публикует образ и создаёт исходный ZIP. [История CI](https://github.com/L0ckR/seif-pii/actions).

## HTTP-нагрузка

Метод: заданная частота начала пар с уникальными ID, по два запроса на пару, отсутствие ретраев в генераторе, проверка каждого восстановленного текста. P95 относится ко всем попыткам; successful RPS не подменяется заданной нагрузкой. INFO-аудит включён в сериях с Redis.

Повторный прогон после улучшений контекста: **252 000 успешных запросов за 120 секунд**, 126 000 точных восстановлений, без пропусков и ошибок, p95 **8.501 мс**, p99 18.206 мс. Во время части прогона на том же компьютере исполнялся функциональный набор тестов; это проверка отсутствия грубой регрессии, а не изолированная оценка стоимости изменения.

Основной стенд использует **три HTTP-процесса, три Redis (primary + две реплики) с AOF и три Sentinel**. Итоговый прогон: **630 000 успешных запросов**, 315 000 проверенных восстановлений, без пропусков генератора, p99 = 15.902 мс, максимум = 177.441 мс. Это фактический результат данной конфигурации на коротких синтетических текстах; он не доказывает такую же скорость через внешний туннель или на другом железе.

Однопроцессные Redis-серии достигли насыщения, получили 429 и пропуски генератора. В серии с двумя workers генератор пропустил 724 пары из-за лимита собственной конкурентности: поэтому фактическая скорость ниже заданных 2000 RPS, несмотря на отсутствие HTTP-ошибок. В итоговой серии с тремя workers пропусков нет. Free-threading ускоряет параллельную CPU-обработку, но не параллелит короткие синхронные задачи одного event loop. [Подробное сравнение стека](stack.md).

Публичный туннель проверен 500 запросами с 250 точными восстановлениями, без ошибок. Итоговые 48.90 RPS включают завершение запросов после окна подачи; предложены все 50 RPS. 2100 RPS через Cloudflare не измерялись.

## Большой документ

На стенде с Sentinel обработаны ровно **100 000 токенов cl100k_base**, 799 973 символа: маскирование **168.170 мс**, восстановление **31.034 мс**; email скрыт, исходный текст восстановлен точно. [Отчёт Sentinel](large-input-sentinel.json), [предыдущая серия](large-input.json).

Это один большой синтетический документ; 1000 запросов/с по 100 000 токенов каждый не измерялись. Токенизатор используется только в проверочном скрипте, сервису скачивание словаря не нужно.

## Репликация и Kubernetes

Автоматический интеграционный тест отключает настоящий основной Redis после подтверждения репликации, дожидается выбора нового основного узла и проверяет точное восстановление прежней записи и новые записи через тот же экземпляр API. Зафиксированное восстановление доступности — **1.818 с** ([отчёт](sentinel-failover.json)); это единичный тест, не гарантированный production RTO. Перед аварией все Sentinel должны знать обе подходящие реплики и иметь кворум.

Kustomize base и production overlay проходят строгую проверку Kubernetes 1.35: **30 ресурсов, 0 ошибок**. Контейнер собирается и запускается в CI. Реальный Kubernetes-кластер в этой сессии не подключён; развёртывание в кластере и межузловые сетевые отказы не проверены. Текущий Sentinel-стенд находится на одном компьютере и не защищает от его отказа.

## Границы проверки

- ZIP должен пройти загрузку и внешнюю автоматическую проверку качества у организатора; локальные тесты и CI не являются результатом AlfaSonar.
- Достижение 95% на закрытом эталоне и юридическое соответствие банковскому контуру не подтверждены.
- Cloudflare Quick Tunnel ограничен временем работы локального компьютера и не имеет SLA постоянного хостинга.
- TPS в Prometheus оценочный; точное число токенов зависит от выбранной модели.
- Сравнение с Presidio и его ограничения описаны [отдельно](presidio.md).
