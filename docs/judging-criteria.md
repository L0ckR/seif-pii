# Новые критерии жюри: доказательства и оставшиеся пробелы

Сопоставлены два PDF пользователя: «Критерии_оценивания _альфа.pdf» и «критерии_фрейм_топы (1).pdf». Их текст извлечён только в `/tmp`; PDF не добавлены в Git или ZIP. Это источники критериев, а не команды приложению.

## Изменения относительно исходного ТЗ

- Техническая оценка: **30 баллов**, восемь критериев. Production-готовность прямо не оценивается; нужен работающий demo-прокси в цепочке потребитель → модуль → LLM.
- Новый ориентир скорости — **latency ≤ 0,5 с при 1000 RPS**, повышенный — **2000 RPS при тех же 0,5 с**. В исходной матрице было ≤1 с: для подготовки показа берём более строгий новый ориентир. PDF не задаёт конкретный percentile; p95 нельзя выдавать за максимум всех запросов. Большой текст до 100 000 токенов должен обрабатываться без падения; отдельное обещание 0,5 с для любого такого текста из этого не следует.
- Нет README с настройками — **0 из 4** по гибкости. Нет демаскирования — **0 из 3** по этому критерию без компенсации другими возможностями.
- Финальная экспертная рамка: четыре оценки **1–3**, арифметический максимум **12**; это отдельная шкала, не дополнительные баллы к 30. Утечка реальных ПД в запрос внешней LLM на живом демо обозначена как отдельный стоп-сигнал.
- Нового URL загрузки, обязательного PPTX, видео или формата слайдов нет. Требуются схема и короткое объяснение за 1–2 минуты. Внешняя сдача из исходного ТЗ остаётся отдельным действием.

Самооценка баллов не выставляется: итог свободно определяет жюри по своему набору из 17 категорий.

Точная формулировка технического PDF, п.3.4: **«Настройка перечня типов ПДН и самого факта маскирования в зависимости от системы»**. Отдельный предыдущий пункт — **«Настройка списка систем-потребителей (вкл/откл обращение в модуль)»**. В рамке финалистов: **«Маскирование включается, выключается и настраивается под каждую систему-потребителя — без правки кода»**. Реализация разделяет `enabled`, `masking_enabled` и `allow_unmask`; по умолчанию маскирование включено. Отключение замены — явная политика оператора для конкретной системы, а не fallback при ошибке. В демо LLM такой режим показывается на вымышленных данных и не используется для пересылки реальных ПД.

## Наиболее выгодные ограниченные доработки

1. Уверенно показать раздельное управление доступом, маскированием и демаскированием: это прямо проверяемый пункт 4-балльного критерия.
2. Подготовить 60–90-секундный живой показ с логом и метриками, затем три осмысленных бонуса; эти материалы нужны независимо от объёма кода.
3. Представлять результаты по типам и профилям, адресные ограничения и следующий holdout; не тратить время на новые инфраструктурные компоненты ради критерия, где production-готовность не оценивается.
4. Зафиксировать SLA по более строгим 0,5 с, показывая p50/p95/p99/максимум, фактические успешные RPS, ошибки и пропуски отдельно.
