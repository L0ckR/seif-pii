# Проверка GLiNER после исправлений RuBERT

**Пересчитать GLiNER с текущими правилами действительно стоило. Это сделано
на всех 5 095 текстах без повторного GPU inference. Аналогичная RuBERT ошибка
декодирования в проверенном GLiNER-профиле не установлена.** Расширение GLiNER
с двух до полного набора PII-типов остаётся отдельным необходимым экспериментом.

Новые агрегаты: [`gliner-recheck-metrics.json`](gliner-recheck-metrics.json).
Основной [`experiment-metrics.json`](experiment-metrics.json) уже использует
обновлённые значения spaCy и GLiNER, сохраняя старые в `historical_mask_f1`.
Тексты и полные локальные кэши в презентацию не включены.

## Что различается в декодерах

RuBERT — token classifier с BIO-предсказаниями. Его прежняя схема объединения
субтокенов отличалась от word decoder pii-guard; обнаруженная Unicode-ошибка
была связана с отсутствующими после токенизации словами и сдвигом соответствия
между словами и метками. Эти причины нельзя автоматически переносить на другую
архитектуру модели.

GLiNER 2.5 использует boundary/span decoder: получает пары границ сущностей
для заданных запросов-меток. Наш PyTorch adapter передаёт исходный текст
официальным `extract_entities` / `extract_entities_long`, проверяет тип,
start/end, конечный confidence и равенство `text[start:end]` возвращённому span.
Короткий текст имеет предел 385 слов с резервом для добавляемой upstream точки;
длинный обрабатывается окнами 384 слова с перекрытием 64.

ONNX заменяет только encoder и boundary head. Остаются те же native
предобработка, сборка схемы, декодер и разрешение пересечений. В adapter
сохраняются `null_logits` для abstention; вместо жадного выбора используется
native weighted interval scheduling. Формы, типы и допустимые границы tensor
outputs валидируются, некорректные результаты не превращаются в пустую выдачу.

**Совпадение native/ONNX на 5 095 из 5 095 текстов доказывает паритет конверсии,
но не независимую правильность общего декодера.** Обе реализации могут разделять
ошибку в общей зависимости; поэтому дополнительно проверена предобработка.

## Что проверено без модели

Строгая CPU-проверка установленного `gliner2==2.0.0` выполнила официальную
предобработку с `error_policy="raise"` для **5 095 документов / 5 179 окон**,
из них **80 длинных документов**. Проверены число исходных слов и строк offsets,
число word embeddings routing positions и попадание этих позиций в токены.

- Ошибок строгой предобработки: **0**.
- Несовпадений word/offset counts: **0**.
- Routing indices вне последовательности: **0**.
- Слов, исчезнувших после токенизации: **0**.

Следовательно, на этом фиксированном наборе воспроизведения RuBERT-подобного
сдвига не обнаружено. Это не доказательство корректности GLiNER для всех
возможных Unicode-входов и не новый замер нейросетевого качества.

В зависимости остаётся отдельное архитектурное ограничение: публичный
inference collator по умолчанию допускает fallback record при исключении.
Строгая проверка подтверждает отсутствие таких ошибок на данном корпусе,
но для дальнейшего расширенного inference стоит явно контролировать этот
режим. Runtime в этой проверке не менялся.

Для tokenizer использован официальный `load_extractor_tokenizer`: он
обрабатывает legacy metadata `extra_special_tokens` как список. Прямой вызов
Transformers loader без helper не совместим с этой записью. Это уже обработанная
зависимостью особенность загрузки; она не является обнаруженной ошибкой
исторических предсказаний GLiNER.

Исходники processor/decoder/chunking и tokenizer зафиксированы SHA-256 в
локальном `preprocessing.json`. Старые отчёты фиксировали версии пакетов,
но не каждый файл установленных зависимостей; текущий аудит не доказывает
побайтовую идентичность всех исторических package files.

## Какие типы GLiNER видел в старом эксперименте

Выбранная `described-names` схема содержала **person, location, organization**.
Последний тип намеренно использовался как конкурирующая метка и не возвращался
как PII. В полном кэше GLiNER сохранились **1 660 PERSON и 1 323 LOCATION**.
Максимальная длина возвращённого span — **44 символа**, существенно ниже
прежнего лимита 200. Ошибок контракта и inference в scored cache нет.

Телефоны, паспорта, карты, СНИЛС, ИНН и другие документные типы в этой схеме
**не запрашивались у модели**. Поэтому здесь нет аналога RuBERT, который уже
предсказывал 21 категорию, а транспорт терял 19 из них. У GLiNER отсутствующие
категории нельзя восстановить из старого кэша: нужен новый inference с заранее
определённой полной PII-схемой.

Порог 0,8, abstention и exclusion ORGANIZATION были частью объявленного
алгоритма. Их наличие само по себе не доказывает ошибку декодирования. Подбор
порога после просмотра результатов нельзя выдавать за исправление багов.

## Пересчёт через текущие правила

Сначала прежний сервис из commit `0ab6d876008af27ee015167ea50488be9d488fb7`
полностью воспроизвёл сохранённые aggregate P/R/F1/TP/FP/FN для spaCy,
GLiNER PyTorch и ONNX на каждом корпусе. После этого те же spans и confidence
прошли текущие `detect → merge_ner_candidates → mask → restore_exact`.
Состав и порядок текстов, gold, кэши и исходники проверялись хешами до и после.

F1 фактического маскирования всех размеченных букв и цифр, проценты:

| Модель + правила | Organizer, 446 | PII-Bench, 1 810 | RedMadRobot, 2 839 |
|---|---:|---:|---:|
| GLiNER: прежние правила | 97,4598 | 71,7599 | 65,6560 |
| **GLiNER: текущие правила** | **97,4598** | **74,2888** | **70,4692** |
| spaCy: прежние правила | 96,8856 | 71,9545 | 59,4971 |
| **spaCy: текущие правила** | **96,8856** | **74,3979** | **65,3661** |
| RuBERT TRT: текущий сервис | 97,1285 | 77,8639 | 93,9041 |

GLiNER PyTorch и ONNX дают одинаковые значения также после нового merge.
Прирост GLiNER — **+2,5289 п.п. PII-Bench и +4,8132 п.п. RedMadRobot** —
возникает от обновления правил и интеграции, а не от изменения модели.

Текущее сравнение теперь использует одинаковые правила для первых трёх
семейств, однако нейросетевые схемы всё ещё различаются: GLiNER/spaCy имеют
PERSON/LOCATION, RuBERT — 14 семейств. GLiNER выше RuBERT на organizer, RuBERT
выше на двух публичных корпусах. Финальный ранг полной GLiNER PII-конфигурации
этими результатами не определён.

RMR exact common14 после новых правил: GLiNER **41,7465%**, spaCy **42,2018%**,
RuBERT **86,7601%**. Это точный тип и исходная граница, а не mask F1; крупные
ФИО/LOCATION spans прежних GLiNER/spaCy не соответствуют компонентной разметке
RMR. Эти числа нельзя смешивать с историческим coarse/adjacency scorer.

**Нового RPS не измеряли.** Прежние GLiNER 31,89/49,86 RPS остаются результатом
старого HTTP runtime и короткого C4/446 протокола. CPU replay не подтверждает
скорость текущих правил. LFM и прежний RuBERT в общей таблице остаются
историческими конфигурациями с явной пометкой.

## Следующий осмысленный эксперимент

На отдельной GLiNER-ветке зафиксировать до inference полную схему PII, словарь
типов, правила приоритета и пороги; сохранить PERSON/LOCATION профиль как
контроль. Проверить strict preprocessing и исходные Unicode offsets, выполнить
inference всех 5 095 неизменённых текстов и оценить одновременно full-mask F1,
точные типы/границы и PERSON isolation. Затем измерить HTTP в одинаковом с
RuBERT протоколе. Расширение числа query labels может изменить и качество,
и стоимость inference — прежний RPS для него неприменим.

В этой работе **не изменялись модель, production/runtime, ветки GLiNER,
разметка или старые отчёты; GPU inference не запускался**. Рабочие копии
`experiment/gliner25-multi` и `experiment/gliner25-onnx` были чистыми.

Organizer по-прежнему предварительная AI silver-разметка, не официальный
gold организаторов. Все три корпуса уже использовались в разработке;
пересчёт — регрессионная оценка, не независимый blind holdout.
