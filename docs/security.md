# Модель безопасности и границы применения

СЕЙФ — работающий прототип локального шлюза защиты персональных данных. Включённые механизмы не являются сертификатом соответствия законодательству РФ, требованиям ЦБ или внутренним стандартам конкретного банка; такие выводы требуют проверки окружения, данных, процессов и политики организации.

## Поток данных

```text
доверенная система → проверка ключа и политики → локальный детектор
                                               ↓
                                    маска / токены / синтетика → LLM
                                               ↓
                             TTL-хранилище зашифрованных соответствий
                                               ↑
доверенная система ← демаскирование известного результата ← ответ LLM
```

Сервис не отправляет текст во внешние модели или аналитические сервисы. HTTP-текст существует открытым в памяти процесса во время обработки; TLS и защищённый хост обеспечиваются окружением. Детектор возвращает типы и смещения, без копий значений в сущностях ответа.

## Реализованные меры

| Угроза | Защита |
|---|---|
| Посторонняя система вызывает API | Явный список систем, флаг `enabled`, сравнение ключа через `hmac.compare_digest`; исключение для явно включённого `demo` |
| Одна система восстанавливает данные другой | Ключ соответствия включает систему и ID; ключи хранилища и отпечатки текста вычисляются HMAC; соответствие из другого пространства недоступно |
| Чтение или подмена сохранённых соответствий | AES-256-GCM со случайным nonce и привязкой к ключу записи как associated data; ошибка аутентификации ciphertext даёт безопасный отказ |
| Лишние копии исходного текста | Хранятся маскированный текст и только заменённые исходные сегменты в ciphertext; при `allow_unmask: false` исходные сегменты не сохраняются |
| Длительное накопление ПД | TTL; фиксированный лимит записей и байтов для памяти; Redis TTL и `maxmemory`/`noeviction` для промышленной схемы |
| Перезапись соответствия повтором или гонкой | Отпечатки исходного и маскированного текста, конфликт для другого содержимого; атомарный `put_if_absent` / Redis `SET NX` |
| Потеря соответствия при сбое хранилища | Fail-closed `503`; нет автоматического переключения Redis на независимую память, которая нарушила бы корреляцию |
| Текст ПД отражается в ошибке | Обработчик валидации заменяет стандартные подробные ошибки; внутреннее исключение не отправляется клиенту и не записывается со значениями |
| Утечка через аудит или метрики | Собственный request ID, фиксированные имена маршрутов/стадий, типы, режим и время; нет payload, `payload_id`, замаскированного текста или API-ключа |
| Неконтролируемый объём запроса и состояние | Ограничены тело запроса, размер текста, длина ID, число одновременных запросов, RPS системы и размер памяти; общий бюджет буферов тел 64 MiB на процесс, отдельный ограниченный CPU-пул для длинных текстов, `429` с `Retry-After` |
| Вредоносное расширение правил | Настройки изменяет оператор, выражения ограничены длиной и временем работы; ошибки обнаружения останавливают обработку |
| Чужой токен в ответе модели | Детокенизация выполняется только по карте данного tenant + ID; неизвестный токен даёт `409`, замена выполняется одним проходом |
| Секреты в сборке | Мастер-ключ и ключи систем берутся из окружения; исходный архив не должен содержать `.env`, рабочие ключи и дампы |

Проверки этих свойств находятся в `tests/test_api.py`: изоляция систем, auth, целостность ciphertext, TTL, ошибки, одновременные повторы, отсутствие исходных значений в логах и метриках. Chunked-запросы резервируют общий бюджет перед добавлением каждого блока; бюджет освобождается при завершении, отказе или отмене запроса. Отмена HTTP-запроса не освобождает слот CPU до завершения реальной работы; исключение после отмены не попадает в стандартный журнал необработанных asyncio-ошибок. При остановке приложения рабочие задачи завершаются без блокировки event loop, ресурсы закрываются также при ошибке startup. Тесты используют только искусственные значения.

## Существенные ограничения

- Детекция на правилах может пропустить новые форматы, контекст, опечатки, обфускацию и неоднозначные ФИО. Успешный HTTP-ответ не доказывает отсутствие всех персональных данных; для банковской эксплуатации нужен представительный закрытый набор, анализ ошибок и согласованные правила допуска.
- `mask` сохраняет пунктуацию и структуру, поэтому раскрывает форму значения; типизированные токены раскрывают тип. Это осознанные свойства режима, а не криптографическое обезличивание.
- Точное обратное преобразование `mask`/`synthetic` рассчитано на неизменённый результат; для изменяемого LLM-ответа используется `token`. Пропуск, исправление или разрыв токена моделью нельзя безусловно восстановить.
- Истечение TTL или перезапуск одноразового memory-стенда делает восстановление недоступным (`410` на явном `/v1/unmask`). На `/process` неизвестный ID считается новым по контракту; TTL должен превышать окно прохождения пары и ретраев.
- Ключ в окружении не заменяет KMS/HSM, разграничение доступа к процессу и управление ротацией. Ротация мастер-ключа без миграции делает существующие записи нечитаемыми; она требует отдельной процедуры.
- Метрики HTTP и rate limiting в одиночном процессе не являются средствами защиты всего сетевого периметра. При нескольких экземплярах общие соответствия и rate state требуют Redis, одинаковых политик и общего мастер-ключа; `max_inflight` и CPU-пул ограничиваются отдельно в каждом процессе. Штатный `scripts/serve.py` задаёт общий каталог multiprocess-метрик до импорта Prometheus и агрегирует workers своего supervisor; разные контейнеры должны опрашиваться отдельно.
- Redis Sentinel автоматизирует выбор нового primary, но асинхронная репликация допускает потерю недавнего подтверждённого соответствия при отказе. Нельзя обещать нулевой RPO; нужны согласованные требования к репликации, размещению, доступности, резервированию и отдельные проверки отказа/восстановления. Неизвестное соответствие не должно подменяться незашифрованной копией или fallback-хранилищем.
- Ограничение пользовательского регулярного выражения по времени не заменяет ограничение доступа к конфигурации. Пользователь API не может передавать новые правила в теле запроса.

## Демонстрационный туннель

Публичный Cloudflare/VK-туннель предназначен для показа искусственных примеров и внешней проверки задания. Провайдер туннеля участвует в передаче запроса, локальный компьютер должен оставаться включённым, а процесс туннеля — работать; это не гарантированный банковский периметр или SLA. Через публичный анонимный стенд не следует обрабатывать реальные клиентские данные.

Для размещения в банковском окружении выбирают управляемый TLS-периметр, сетевую изоляцию, защищённое общее хранилище, ключи и доступ операторов; проверяют журналы reverse proxy, APM, WAF и резервные копии, поскольку приложение не управляет их содержимым. Демонстрационное исключение выключают (`SEIF_DEMO=0`), системы и их ключи задают явно. Критерии юридического соответствия и разрешённые трансграничные маршруты определяет организация в рамках отдельной проверки.

## Что намеренно не обещается

Не заявляются нулевые утечки при любом входном тексте, сертификация, устойчивость 1000/2000 RPS на любом оборудовании, 95% на закрытом наборе или доступность публичного туннеля после остановки компьютера. Проверяемые результаты — тесты, сохранённые отчёты качества/нагрузки и факт внешнего запуска — приводятся отдельно от этих ограничений.
