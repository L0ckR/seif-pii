# RuBERT: пропускная способность на корпусе организаторов

Изолированный эксперимент проверяет, сколько **новых маскирований в секунду**
выдерживает текущий сервис с RuBERT на 446 уникальных текстах организаторов.
Повторяются полные циклы корпуса; тексты и ожидаемые ответы не подменяются
синтетическими примерами. Кэш результатов в сервисе отсутствует.

## Измеренные результаты 23 сентября 2026

Одна RTX 4070 Ti SUPER 16 GB, Ryzen 7 7800X3D, WSL2. API и генератор:
Python 3.14t без GIL; NER: Python 3.12, TensorRT 10.13.3.9, FP16.
Генератор и сервис используют один компьютер. Ниже **новые маскирования/с**,
а не сумма mask + restore. Это короткие closed-loop прогоны после прогрева.

| Конфигурация | Хранилище | Mask RPS | p95, мс | Отчёт |
|---|---|---:|---:|---|
| 1 API + 1 NER, batch 16, исправленный HTTP transport, C32 | память | 733 | 64.8 | [b16-sharded.json](b16-sharded.json) |
| 2 API + 2 NER, batch 16, исправленный HTTP transport, C32 | память | 1 147 | 52.2 | [b16-sharded.json](b16-sharded.json) |
| 6 API + 2 NER, batch 32, C64 | Redis | 1 791 | 62.9 | [cluster-6api-2ner-v2.json](cluster-6api-2ner-v2.json) |
| 8 API + 2 NER, batch 32, C64 | Redis | 1 964 | 53.2 | [cluster-8api-2ner.json](cluster-8api-2ner.json) |
| 8 API + 2 NER, batch 32, C128 | Redis | 2 011 | 142.8 | [cluster-8api-2ner.json](cluster-8api-2ner.json) |

Каждая строка прошла без HTTP-ошибок и расхождений с эталонным ответом.
В последнем прогоне по 13 380 запросов на фазу; измерение заняло около 6.7–6.8 с.
Это подтверждение кратковременной мощности, а не доказательство устойчивости
входящего потока 2 000 RPS. Шесть API использовали четыре CPU threads на NER,
восемь API — один; эти две строки не изолируют только влияние числа API workers.

Отдельный HTTP NER с двумя процессами и batch 32 достиг 2 985 документов/с
([replicas-b32.json](replicas-b32.json)). Он исключает API, правила, маскирование
и vault, поэтому его нельзя выдавать за RPS всего сервиса. Исторические
`replicas-b1.json`, `replicas-b32.json` и `b16-sniffio.json` фиксируют промежуточные
варианты до окончательной оптимизации транспорта, с fingerprint каждого варианта.

### Сохранение качества

[quality-b32.json](quality-b32.json) проверяет новый GPU inference всех
**5 095 документов**: Organizer 446, PII-Bench 1 810, RedMadRobot 2 839.
Все исходные типизированные границы, сущности сервиса, confidence и готовые
маски совпали с сохранёнными предсказаниями текущей модели. Это отсутствие
регрессии от batching, а не 100% правильность относительно разметки.
После этой проверки изменялась только настройка CPU threads через env и
закрытие HTTP transport при отмене задачи; веса, decoder и правила прежние.

### Что ускорено

- Отдельные HTTP-запросы объединяются в ограниченный GPU microbatch до 32
  документов с ожиданием до 2 мс. Сохраняются порядок и исходные offsets.
- Независимые TensorRT contexts и CUDA streams на batch/length shape позволяют
  использовать CUDA graphs; общие mutable buffers защищены блокировкой модели.
- API ограничивает параллелизм NER настраиваемым semaphore. Небольшие независимые
  HTTP pools сокращают CPU-стоимость обхода соединений под высокой нагрузкой.
- Установлен `sniffio`: HTTPcore раньше повторял неудачный import на каждой
  операции. Это устраняет измеренную CPU-стоимость без изменения предсказаний.
- Процессы API и NER масштабируются независимо; общий Redis и один master key
  позволяют восстановить текст через другую API-реплику.

Первый `cluster-6api-2ner.json` имеет `FAIL`: `redis-server` отсутствовал в PATH,
нагрузка не запускалась. Исправленный запуск сохранён отдельно с суффиксом `v2`.

## Что именно сравнивается

1. Один, два или четыре независимых процесса NER на **одной физической GPU**.
2. На каждый процесс NER приходится отдельный процесс основного API.
3. Генератор распределяет запросы между парами API + NER по round-robin.
4. Отдельная фаза `/analyze` измеряет NER с его HTTP, очередью и декодером.
5. Фаза `/v1/mask` измеряет весь путь: API, правила, NER, слияние,
   маскирование и запись в зашифрованное хранилище в памяти.
6. Опциональный динамический batch задаётся отдельно от числа процессов;
   размер batch = 1 оставляет одиночный inference.

В `http_scaling.py` это **не развёрнутый production-кластер**: каждый API использует отдельное
хранилище в памяти. Восстановление направляется в исходный экземпляр API.
Для общего адреса с произвольной маршрутизацией нужен общий Redis и одинаковая
конфигурация ключей. Прокси, Redis, облачный туннель и запись входящих запросов
в этих измерениях не участвуют. Несколько процессов на одной GPU делят её
память и вычислительные ресурсы; линейное масштабирование не предполагается.

## Протокол

- Decoder `word`, профиль `native`: 21 исходный класс модели отображается
  в 14 классов сервиса. Веса и правила не меняются между фазами одного запуска.
- Используются те же сохранённые предсказания Organizer, что в последнем
  `rubert-upgrade`. Они служат только эталоном сравнения, не ответами сервера.
- Каждый `/v1/mask` получает новый случайный `payload_id`; повторных отправок
  при ошибках нет. Каждая попытка и её ошибка остаются в знаменателе.
- Для каждого успешного маскирования проверяются точный результат,
  упорядоченные границы и типы сущностей, а также список типов ответа.
- Для direct NER проверяются схема ответа и точные типизированные границы.
  Float confidence может меняться, его численное равенство не требуется.
- Инструментация каждого NER считает начатые и завершённые документы,
  активную работу и HTTP-коды. Счётчик API проверяет прохождение NER-стадии.
  При batch отдельно сохраняется распределение фактических размеров batch.
- Измерение считается успешным только при отсутствии ошибок, полной
  эквивалентности эталону и совпадении количества запросов с реальным NER.
- TensorRT warmup, пять синтетических маскирований на replica, чтение
  метрик, до восьми точных восстановлений после каждой фазы и проверка
  отказа при остановке NER исключаются из расчёта RPS.
- SHA-256 исходного кода, корпуса, эталонных предсказаний и файлов модели
  фиксируются до запуска. Неизменность проверяется вокруг каждой фазы и
  после полного запуска. Полные файлы отчёта не перезаписываются.
- По умолчанию JSON содержит агрегаты. Исходные тексты, найденные значения,
  ключи доступа и идентификаторы запросов не записываются в отчёт.
  `--include-traces` добавляет только идентификатор строки корпуса и
  метаданные попытки. Логи неудачного запуска остаются в игнорируемом
  `local-data/rubert-throughput/`, с правами доступа 0600.

## Запуск

Из корня репозитория, после установки локальной модели и зависимостей
GPU-сервиса. Генератор и API работают на Python 3.14t, NER — в отдельной
среде с TensorRT. Пути интерпретаторов сохраняются без разыменования
символической ссылки, чтобы не обходить `pyvenv.cfg`.

Предварительная проверка корпуса и артефактов, **без запуска GPU**:

```bash
/home/lockr/projects/seif-pii/.venv/bin/python \
  benchmarks/ner-models/rubert-throughput/http_scaling.py \
  --model-path /home/lockr/projects/rubert-pii-fast/publish/tensorrt \
  --reference-cache local-data/rubert-upgrade/run-v2/organizer.jsonl \
  --dry-run \
  --output local-data/rubert-throughput/preflight.json
```

Короткий контроль одиночного inference и двух процессов, 4 460 запросов
на каждую фазу:

```bash
/home/lockr/projects/seif-pii/.venv/bin/python \
  benchmarks/ner-models/rubert-throughput/http_scaling.py \
  --model-path /home/lockr/projects/rubert-pii-fast/publish/tensorrt \
  --reference-cache local-data/rubert-upgrade/run-v2/organizer.jsonl \
  --replicas 1 2 --concurrency 16 32 --stages ner mask --repeats 10 \
  --ner-max-jobs 32 --ner-max-http 64 --api-ner-concurrency 32 \
  --batch-size 1 \
  --output benchmarks/ner-models/rubert-throughput/replicas-b1.json
```

Для воспроизведения прежней границы очередей используются
`--ner-max-jobs 4 --ner-max-http 16 --api-ner-concurrency 4`.
Высокая конкуренция с короткой очередью может давать отказы; такой результат
сохраняется, но не считается доказательством успешной пропускной способности.

Для следующей фазы можно задать `--replicas 1 2 4`,
`--concurrency 8 16 32 64`, `--repeats 20`, а размер batch —
`--batch-size 8`, `16` или `32`. `--ner-max-jobs` должен быть не меньше
batch, а `--ner-max-http` — не меньше очереди модели.
Каждый вариант пишет в **новый файл**. Несколько таких запусков не следует
выполнять одновременно на одной GPU.

## Как читать результат

- `successful_mask_rps`: только успешные HTTP-маскирования; direct NER
  имеет здесь `null` и отдельное `successful_rps`.
- `reference_matching_rps`: запросы, совпавшие с эталоном; при нарушении
  эквивалентности эта величина меньше успешного HTTP throughput.
- `latency_ms_all_attempts`: p50/p95/p99 и максимум по всем попыткам,
  включая ошибки. Тайминг заканчивается после получения полного ответа.
- `valid_successful_measurement`: пригодность фазы для заявления
  «этот throughput подтверждён без потери ответов и изменения результата».
- `OVERLOAD`: хотя бы одна фаза не прошла критерий; следует смотреть ошибки,
  эквивалентность и очереди конкретной фазы. Это не автоматически GPU-предел.
- `FAIL`: ошибка подготовки, исполнения или проверок, требующая разбора.

Этот генератор использует **closed-loop**: фиксированное число одновременных
запросов. Даже значение выше 2 000 успешных маскирований/с само по себе
не подтверждает устойчивую работу при внешнем потоке 2 000 RPS. После выбора
конфигурации нужен отдельный open-loop endurance-прогон с проверкой потерь,
p95/p99, памяти и общего Redis.

До GPU-запуска проверены синтаксис, CLI, подготовка всех 446 случаев без
GPU, счётчики batch-документов и расчёт успешного throughput при ошибках.
Результаты GPU-запусков должны читаться из фактических JSON этого каталога;
планируемые конфигурации не являются измерениями.

## Реплики с общим Redis и фиксированный входящий поток

`cluster_scaling.py` запускает два NER и два listener API, каждый с четырьмя
Uvicorn workers. Все восемь API используют общий Redis DB0, master key и policy.
Перед нагрузкой проверяются разные PID внутри каждой группы и точное
восстановление через другую группу. После open-loop восемь сохранённых
результатов восстанавливаются через соседнюю группу, без дополнительных NER-вызовов.
Исторические closed-loop отчёты `cluster-6api-2ner-v2.json` и
`cluster-8api-2ner.json` ещё использовали разные Redis DB/key между группами:
в них гарантируется только cross-worker restore внутри группы.

Redis запускается отдельно с временным паролем, Unix socket и отключённой
персистентностью; существующие Redis-инстансы не используются. JSON сохраняет
агрегаты памяти и число ключей. Это локальный процессный стенд: TCP Redis,
HAProxy, Docker, Cloudflare и запись исходных запросов в его RPS не входят.
Compose с двумя API-контейнерами, двумя NER и HAProxy подготовлен отдельно:
[deploy/rubert](../../../deploy/rubert/README.md). Его конфигурация и маршрутизация
проверены, но запуск GPU-контейнеров и их throughput пока не измерены.

Пример фиксированной нагрузки 2 000 **новых маскирований/с** в течение минуты:

```bash
/home/lockr/projects/seif-pii/.venv/bin/python \
  benchmarks/ner-models/rubert-throughput/cluster_scaling.py \
  --redis-server /tmp/seif-redis/runtime/usr/bin/redis-server \
  --model-path local-data/rubert-tensorrt/model \
  --reference-cache local-data/rubert-upgrade/run-v2/organizer.jsonl \
  --replicas 2 --api-processes-per-replica 4 \
  --batch-size 32 --batch-wait-ms 2 --cpu-threads 1 \
  --api-cpu-workers 1 --api-ner-concurrency 16 \
  --ner-max-jobs 128 --ner-max-http 256 \
  --offered-rps 2000 --duration 60 --max-inflight 256 \
  --output local-data/rubert-throughput/new-open2000-60s.json
```

Путь Redis — пример локального runtime, его нужно заменить своим. `--redis-server`
можно опустить, если команда доступна в PATH. Для распакованного Debian runtime
используется также его `LD_LIBRARY_PATH`; обычной установке это не требуется.
Символическая ссылка исполняемого файла сохраняется: некоторые Redis packages
выбирают режим server/check-rdb по имени запуска. Первый
`cluster-8api-2ner-open2000-60s.json` завершился до нагрузки из-за этой особенности;
исправление находится в текущем driver, повторный отчёт имеет суффикс `v2`.

`valid_successful_measurement` требует отсутствия пропусков генератора,
ошибок HTTP и расхождений с эталоном; оно **не заменяет проверку задержки**.
`scheduled_arrival_mask_latency_ms` включает задержку отправки у генератора,
`response_latency_ms` считает фактический HTTP roundtrip. Отдельный
`latency_budget` показывает количество превышений 500 мс, долю своевременных
корректных ответов от всех предложенных запросов и максимум. Требование
0.5 с из критериев не задаёт percentile, поэтому p95 не доказывает выполнение
предела для каждого запроса. Пропуски нельзя исключать из доли успешных ответов.

### Фиксированные 2 000 RPS: восемь API

[Минутный прогон](cluster-8api-2ner-open2000-60s-v2.json) предложил 120 000
новых запросов. Обработаны **117 247**, все ответы точны, ошибок HTTP нет;
**2 753 (2.294%)** не отправлены из-за лимита 256 одновременно активных запросов.
Фактический throughput с завершением остатка — **1 950.69 mask/s**.
Задержка от назначенного времени прихода: p95 **193.15 мс**, p99 **240.49 мс**,
максимум **423.61 мс**, превышений 500 мс нет. Восемь cross-group restore точны.
Итог **OVERLOAD**: короткие 2 011 RPS не превратились в подтверждённые
устойчивые 2 000 RPS без потерь. Лимит генератора является частью этого
протокола; результат не определяет независимо от него абсолютный предел сервера.

Redis вырос с 1.03 MB до 112.01 MB, 117 262 ключа после теста. Это около
947 дополнительных байт на новое маскирование для данного корпуса, включая
накладные расходы. Линейная оценка для 2 000 × TTL 900 даёт около **1.6 GiB**,
без запаса на изменение текстов и аллокатор. Tuned Compose выделяет Redis
maxmemory 4 GiB и RAM limit 5 GiB; полный 900-секундный steady state не проверен.

### Дополнительные процессы и оставшийся CPU overhead

[12 API + 2 NER](cluster-12api-2ner-open2000-60s-v2.json) на тех же 2 000
предложенных mask/s за 60 секунд оказались медленнее: **1 906.34 успешных mask/s**,
5 437 пропусков генератора. Дальнейшее увеличение числа API на одном CPU
не выбрано как решение. Первый запуск без `v2` остановился до нагрузки:
последовательный PID probe не смог обнаружить всех шесть Uvicorn workers.
Теперь probe открывает параллельную серию соединений и по-прежнему требует
увидеть все настроенные PID до измерения.

Во всех перечисленных capacity-прогонах исходные тексты не записывались,
HTTP access log выключен, API log level — `WARNING`: метрики и проверки
работают, но INFO-аудит не выводится. Полная стоимость INFO-аудита и request
capture этими числами не подтверждена. Tuned Compose сохраняет штатный INFO.

Свежий cProfile одного API после sharding: 11.03 млн Python calls за 2 230
маскирований, 6.69 профилированных секунд. Из них около 1.91 с cumulative
приходится на HTTP transport NER, 0.84 с — на detector, 0.205 с — на FastAPI
jsonable_encoder. Cumulative значения вложены, их нельзя складывать.
Профилировщик сильно замедляет код: полученные с ним RPS не являются
измерением мощности. Диагностические `.pstats` хранятся только в `local-data/`.
